# 07. 病薬ロジック × 資料照合レビュー

| 項目 | 内容 |
|------|------|
| 対象実装 | `js/core/ByoyakuCalculator.js`（＋格局・身旺弱依存） |
| 照合資料 | `資料/病薬説_…` `気象篇_…` `喜忌篇_…` `継善篇_…` |
| 結論要約 | **格局別病薬の骨格は概ね妥当。ただし気象・喜忌・継善の順序と気象層が未実装のため、命理正宗の看命手順としては不十分。取り込みが必要。** |

---

## 1. 総合判定

| 観点 | 判定 | コメント |
|------|------|----------|
| 病薬説（第8章相当）の基本形 | △〜○ | 主軸→病→薬、格局別ルール、四病四薬の骨格はある |
| 從重者論 | △ | 計算はあるが、**月令起点の重み付けが弱く、結果にも十分使っていない** |
| 喜忌篇（看命順序） | ✕ | 順序の思想はコード構造に明示されていない |
| 継善篇（主軸を守る） | △ | 格局＝主軸としては入っているが、**「用神損傷」を正面から検査する層がない** |
| 気象篇（寒暖燥湿・清濁） | ✕ | **完全未実装**。病薬前の「局の空気」が無い |

**判定:**  
現行ロジックだけで「病薬説の簡易実装」としては動くが、資料が要求する  
`喜忌（順序）→ 継善（柱）→ 気象（空気）→ 格局 → 病薬`  
の流れにはなっていない。ユーザー要望どおり、三篇の考え方をロジックへ取り込む必要がある。

## 2. 現行ロジックが資料と一致している点

### 2.1 病薬説との一致

| 資料の要点 | 現行実装 | 評価 |
|------------|----------|------|
| 病＝害をなす神、薬＝それを除くもの | 格局別 `disease` / `medicine` | ○ |
| 主軸（財／食傷／官殺／印）ごとの病薬対応 | `kakkyoku_rules.json` + `KAKKYOKU_YOUSHIN_MAP` | ○ |
| 四病（雕枯旺弱）・四薬（損益生長） | `_classifyFourDisease` / `_classifyFourMedicine` | ○（簡易） |
| 複数病の併存 | `diagnoses[]` 複数マッチ | ○ |
| 薬の所在（命式内／なし） | `_findMedicineInChart` | ○ |
| 日干為主 | 通変星・身旺弱・格局いずれも日干基準 | ○ |
| 月令為提綱（格局側） | `KakkyokuCalculator` が月令ベース | ○ |

### 2.2 継善篇と部分一致している点

- 「格局を立て、その格の柱を壊すものを病とみる」流れは、格局別ルールと一致。
- 例: 財格×比劫多 → 比劫奪財／官殺が薬、は継善篇・病薬説の実例と同型。

### 2.3 喜忌篇と部分一致している点

- パイプライン上は `Fortune → Strength → Kakkyoku → Byoyaku` となっており、  
  「日干・月令（身旺弱）→格局→病薬」という**粗い順序**は踏んでいる。
- ただし喜忌篇が強調する「透干／蔵干の区別を喜忌に反映する」「年基根・月提綱・日命主・時分野」は未反映。

## 3. 重大な不一致・欠陥

### 3.1 【重大】気象篇がロジックに存在しない

資料（気象篇）:

```text
先に気象規模 → 後に用神／病薬
寒暖・燥湿・清濁を先に見る
同じ五行でも局の気象で病にも薬にもなる
```

現行:

- 寒暖・燥湿・清濁の判定クラス／フィールドが**一切ない**
- 冬月の冷えを「火／木が薬」と出す経路がない
- 夏月の過熱を「水が薬」と出す経路がない
- 十神ルールだけで薬が決まり、**気象と矛盾しうる**

例（資料の冬月・丁火）:

| 層 | 期待 | 現行が起きやすいこと |
|----|------|----------------------|
| 気象 | 冷え・湿りが病の空気。木火が薬方向 | 官殺多など十神条件だけで印／食傷等に寄り、**調候（暖める）が無視される**可能性 |

→ **病薬の前段に `KishouAssessor`（気象判定）層を必須化すべき。**

### 3.2 【重大】從重者論が「名目だけ」

コメント上は:

1. 日干確認  
2. 月令特定  
3. 從重者論  

とあるが、実体は次のとおり。

| 問題 | 詳細 |
|------|------|
| 月令ブーストなし | `_calcElementDistribution` は四柱を同型加重。月令司令を特別扱いしない |
| `heaviestElement` 未使用 | `diagnose()` で算出するが、以降の分類・戻り値にほぼ使わない |
| 雜気月の扱い | 資料は「從重者論で雑蔵の重い気から入る」と明記。現状は主気0.7／中0.5／余0.3の固定で、月令主気優先の明示ロジックではない |

→ 從重者論を本当に使うなら、**月令起点の重み＋最重五行を病候補の第一候補に接続**する必要がある。

### 3.3 【重大】喜忌篇の「看命順序」がコード契約になっていない

資料の順序（喜忌篇・気象篇を統合）:

```text
日干 → 月令 → 気象 → 透干/蔵干 → 格局 → 主軸(継善) → 病薬 → 喜忌の確定
```

現行の実質順序:

```text
五行分布(均等) → 四病 → 四薬 → 格局ルールで病薬名
```

欠落:

1. 気象を先に確定しない  
2. 「年／月／日／時の役割差」がない  
3. 透干と蔵干の軽重が病薬条件に十分乗っていない（条件は主に天干カウント）  
4. 最終成果物に「喜／忌」の明示がない（病薬と喜忌が混線したまま）

### 3.4 【中〜重大】継善篇の「用神を損傷してはならない」が検査として弱い

資料:

```text
継善 = 柱を立て、壊すものを探す
用神損傷 → それが病
救うもの → 薬
```

現行:

- 格局別 `condition`（比劫多・傷官透出・印多…）で**間接的**にカバー
- しかし次が無い:
  - **用神そのものが損傷されているか**の専用チェック
  - 「無破」（有官有印無破）の成立判定
  - 柱が成立していないのに病薬名だけ出るケースのガード

特に問題になりやすい点:

- `disease.element` に四病側の五行を載せ、`disease.name` は格局ルール側——**病名と病の五行が食い違う**ことがある
- 雕の病では「用神側」を diseaseElement にしており、資料の「害をなす神＝病」とずれる解釈になりうる（雕は「欠け」を病とみる特殊型なので説明が必要）

### 3.5 【中】病と薬の強弱バランスが未実装

病薬説資料の核心表:

| 病重薬重 | 病重薬軽 | 病軽薬重 | 病軽薬軽 | 病なし薬なし |
|----------|----------|----------|----------|--------------|

現行は `severity`（病側）のみで、**薬力の強弱・病薬バランスラベルが無い**。  
気象・継善を入れるなら、ここもセットで入れるべき。

### 3.6 【軽〜中】実装上の粗さ

| 箇所 | 内容 |
|------|------|
| `_evaluateConditions` | `officerElement` を誤計算して捨て、`officerEl` で補正（デッドコード） |
| 中和（strength=neutral） | ルールキーが `strong`/`weak` のみ。中和は strong 側に倒れる |
| 雕の優先 | 「純然無雑＝平常／雕」は資料どおりだが、気象偏枯より先に雕へ入ると本末転倒になりうる |
| 旺の40%閾値 | ヒューリスティック。月令起点の從重と未統合 |

## 4. 三篇をロジックへ取り込む設計方針

### 4.1 役割分担（資料準拠）

| 篇 | ロジック上の役割 | 出力 |
|----|------------------|------|
| 喜忌篇 | 看命パイプラインの順序と柱の重み（日主・月令・透蔵） | `readingOrder`／柱ウェイト |
| 継善篇 | 主軸（守るべき用神／格局の柱）と破格要因 | `pillar`（主軸）, `breaks[]`（損傷） |
| 気象篇 | 病薬前の局の空気（寒暖燥湿清濁）と調候方向 | `kishou`, `choukouDirection` |
| 病薬説 | 病／薬の確定と四病四薬 | 既存 `diagnoses` を拡張 |

### 4.2 推奨パイプライン（病薬オプションON時）

```text
[F-01] 命式算出
   ↓
[喜忌] 日干確定・月令確定・透干/蔵干の整理・柱ウェイト適用
   ↓
[気象] 寒暖・燥湿・清濁を評価 → 調候の方向（温/涼/潤/燥整理）
   ↓
[継善] 格局＋用神カテゴリを主軸化 → 用神損傷（破）を列挙
   ↓
[病薬] 從重者論（月令ブースト）＋損傷リスト＋気象方向で病/薬を決定
   ↓
[表示] 気象要約 → 主軸 → 病 → 薬 →（任意）喜忌ラベル
```

※ 資料の気象篇手順「格局の前に気象」を採る。  
※ 格局計算自体は気象の後でも、入力としては命式があれば可能。  
　**病薬の処方段階で気象を必ず参照する**ことが必須条件。

### 4.3 新規／拡張モジュール案

| モジュール | 責務 |
|------------|------|
| `KishouAssessor`（新規） | 月令＋五行分布から寒/熱/燥/湿/中和、清/濁を返す |
| `KeizenAnalyzer`（新規または Byoyaku 内） | 主軸・用神損傷リスト（破）を返す |
| `ByoyakuCalculator`（拡張） | 気象方向・損傷リスト・月令ブースト從重を入力に病薬を決定 |
| `kakkyoku_rules.json`（維持＋拡張） | 格局別病薬は維持。気象上書きルールを別表で追加可 |

### 4.4 気象判定のたたき台（実装可能な具体規則）

#### 寒暖（月令主＋五行補正）

| 月支 | ベース |
|------|--------|
| 亥子丑 | 寒 |
| 寅卯辰 | 温（春） |
| 巳午未 | 熱 |
| 申酉戌 | 涼（秋） |

補正例:

- 火土スコアが高い → 熱寄りへシフト  
- 水金スコアが高い → 寒寄りへシフト  

#### 燥湿

- 火土重・水弱 → 燥  
- 水重・火弱 → 湿  

#### 清濁（簡易）

- 主軸十神が明確で冲剋・混雑が少ない → 清  
- 官殺混雑・財印両破・冲多 → 濁  

#### 調候方向 → 薬の優先

| 気象 | 調候の薬方向（優先候補） |
|------|--------------------------|
| 寒 | 火（必要なら木で通関） |
| 熱 | 水（必要なら金で生水） |
| 燥 | 水 |
| 湿 | 土（燥土）／火で湿を開く（局による） |
| 濁 | 主軸を乱す十神の整理（継善の破と合流） |

**統合ルール（重要）:**

```text
1. 継善で「用神を傷つける神」を病候補とする（本命）
2. 気象が極端なら、調候不足も病候補とする（並行または上位）
3. 薬は「病を除く十神」と「調候の五行」を突合し、両立するものを優先
4. 両立しない場合は、重症度の高い病を優先し、もう一方を副病として diagnoses に積む
```

### 4.5 継善「用神損傷」チェック案

主軸カテゴリごとの破（例）:

| 主軸 | 損傷（病候補） | 救い（薬候補） |
|------|----------------|----------------|
| 官殺 | 傷官透出・官殺混雑・身弱で官を受けられない | 印制傷／財化傷／印化殺 等 |
| 財 | 比劫多・印多で財滞 | 官殺制比劫／食傷生財 |
| 印 | 財破印（貪財壊印） | 比劫護印／官生印 |
| 食傷 | 印多で食傷を抑える | 財洩食傷／印を破る財 |

これは現行 `kakkyoku_rules` と近いが、**「破の有無」を先に構造化してからルール照合する**点が継善篇の取り込みになる。

### 4.6 喜忌篇の取り込み（ロジック契約）

コード上の必須契約:

1. 日干を主語にする（既存維持）  
2. 月令ウェイトを五行分布・從重に反映（必須追加）  
3. 透干を蔵干より重く数える（病条件・薬所在で既存の差を強化）  
4. 出力に `kiki: { ki: [...], ki_elements, ... }` を任意追加  
   - 薬・調候方向 → 喜側  
   - 病・破 → 忌側  

喜忌は「病薬の別名」ではなく、**病薬確定後のラベル付け**とする（資料: 喜忌＝粗い方向、病薬＝具体処方）。

## 8. 結論

1. **格局別の病／薬対応そのものは、資料の病薬説・継善篇の実例と大きく矛盾しない。**  
2. しかし **気象篇が欠落**しており、「同じ十神でも気象で意味が変わる」という命理正宗の活法が再現できていない。  
3. **喜忌篇の順序・月令提綱の重み、継善篇の用神損傷検査**がロジック契約として弱い。  
4. したがって「資料と照らし合わせて問題ないか」への回答は、  
   **現状のままでは不十分。三篇を前段ロジックとして取り込む改修が必要。**

次ステップ案: 本レビューの P0 を仕様に正式反映し、実装タスクへ落とす。
