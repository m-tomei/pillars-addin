## 2. 結論

補正合成式、子時の2モード、既定値 `switch23`、時差の符号と範囲、真太陽時・DSTを対象外とする基本方針は概ね一致している。

ただし、実装着手前に解消すべき問題がある。特に次の4点は、実装分岐や計算誤りへ直結する。

1. 大運に「補正後時分」を反映する要件と、既存APIを変更しない詳細設計が両立しない
2. 日柱日付解決関数が3名称に分裂している
3. 子時による人工的な翌日扱いの適用範囲が、上位要件では曖昧
4. 地方平均時補正の丸め規則と東京の表示値が要件・詳細設計で異なる

## 3. 指摘一覧

### P0-01 大運への補正後時分を現行APIでは反映できない

- 根拠:
  - `時刻補正機能_詳細設計/02_処理パイプライン.md:75-78,85-94`
  - `時刻補正機能_詳細設計/03_補正アルゴリズム詳細.md:100-103`
  - `時刻補正機能_詳細設計/07_モジュール設計.md:52-56`
  - `時刻補正機能_詳細設計/10_実行計画.md:39-41`
  - 現行 `js/core/GreatFortuneCalculator.js:187-214,259-276`
- 問題:
  - 詳細設計は大運の節入り距離に `t_corrected` を使うとしている。
  - 一方、モジュール設計は「シグネチャ変更不要、呼び出し引数を補正後にするだけ」としている。
  - 現行 `calculateStartAge` は時分を受け取らず、出生日時を常に 12:00 としているため、補正後の時分は節入り距離へ反映されない。
- 推奨:
  - 次のどちらかを要件で確定する。
    1. 時分まで反映する: `calculateStartAge` と節入り探索APIへ時分を追加し、P4/P7へ改修・テストを追加する。
    2. 日付だけ反映する: 「大運は補正後年月日のみ使用し、時分は従来どおり正午固定」と要件・詳細設計を修正する。

### P0-02 日柱日付解決関数の名称が3通りある

- 根拠:
  - `時刻補正機能_詳細設計/02_処理パイプライン.md:15` の `resolveDayDate`
  - 同 `:72` の `resolvePillarDate`
  - `時刻補正機能_詳細設計/04_子時モード詳細.md:44-50,90` の `resolveDayPillarDate`
- 問題:
  - 同一処理が別APIに見えるため、実装・単体テスト・呼び出し側で不一致が発生する。
- 推奨:
  - `resolveDayPillarDate` に統一し、配置先、引数、戻り値、公開/非公開を `07_モジュール設計.md` に明記する。

### P0-03 子時の人工的な+1日の適用範囲が上位要件で曖昧

- 根拠:
  - `時刻補正_v1.5/01_機能要件_補正ロジック.md:105-125`
  - `時刻補正機能_詳細設計/02_処理パイプライン.md:71-78,87-94`
- 問題:
  - 上位要件のフローは、子時の+1日処理後に `FortuneCalculator` へ渡すように読める。
  - 詳細設計では、人工的な+1日は日柱・時干だけに使用し、年月柱の節入り判定と大運には使用しない。
  - 立春や節入りの23時台で誤って年月柱まで翌日基準にすると、柱が変わり得る。
- 推奨:
  - 上位要件を「`t_corrected` は年月柱・大運用」「`resolveDayPillarDate` の結果は日柱・時干用」と明確に分離する。
  - `00_概要とスコープ.md:35`、README、決定事項の影響範囲にも反映する。

### P1-01 地方平均時補正の丸め規則と表示例が不一致

- 根拠:
  - `時刻補正_v1.5/01_機能要件_補正ロジック.md:38-47` は丸め未定義
  - `時刻補正_v1.5/02_UI入出力仕様.md:65-70` は東京 `+18分`
  - `時刻補正_v1.5/03_データマスタと非機能.md:44-47` は `約+18〜19分`
  - `時刻補正機能_詳細設計/03_補正アルゴリズム詳細.md:28-45` は `Math.round` で `+19分`
- 問題:
  - 自動テストの期待値と表示値が一意に決まらない。
- 推奨:
  - 上位要件に `Math.round(4 × (longitudeEast - 135.0))` を明記し、東京を `+19分` に統一する。

### P1-02 補正日時のタイムゾーンと日付加算方式が一本化されていない

- 根拠:
  - `時刻補正_v1.5/00_概要とスコープ.md:11,16`
  - `時刻補正機能_詳細設計/03_補正アルゴリズム詳細.md:47-72`
- 問題:
  - JST前提は概要にあるが、補正後の数値日時をJSTとして節気データと比較する契約がAPI仕様にない。
  - 詳細設計内にも、ローカル `Date` を使う例と、タイムゾーン依存を避ける数値加算の推奨が併記されている。
- 推奨:
  - 正式方式を「JST暦としての数値年月日時分」に統一し、OSタイムゾーンに依存する `new Date(...)` を正規アルゴリズムから除外する。

### P1-03 負の分加算アルゴリズムが実装可能な精度で定義されていない

- 根拠:
  - `時刻補正機能_詳細設計/03_補正アルゴリズム詳細.md:61-72`
  - `時刻補正機能_詳細設計/08_テスト設計.md:19-20`
- 問題:
  - `floorDiv`、正の剰余、`calendarAdd` が名称だけで、JavaScriptでの定義がない。
  - JavaScriptの `%` は負数で負値を返すため、前日跨ぎが実装差になり得る。
- 推奨:
  - `floorDiv(a,b) = Math.floor(a/b)`、`mod(a,b) = ((a % b) + b) % b` を記載する。
  - 月末、年末、閏日、複数日跨ぎのテストを追加する。

### P1-04 AppController擬似コードが有効なAPI仕様になっていない

- 根拠:
  - `時刻補正機能_詳細設計/05_データモデルとAPI.md:95-117`
- 問題:
  - `longitude implicitly via service` はJavaScriptでも具体的な引数契約でもない。
  - `showResults` へ未補正の `input.year` を渡しているため、補正で年を跨ぐと大運表示年が計算基準とずれる可能性がある。
- 推奨:
  - `TimeCorrectionService` がコンストラクタ注入したマスタを使う正式コード例にする。
  - 表示用生年が入力年か補正後年かを要件で決め、補正後基準なら `y` を渡す。

### P1-05 大運・補正×子時の統合テストが不足

- 根拠:
  - `時刻補正機能_詳細設計/08_テスト設計.md:10-64`
- 問題:
  - 大運の節入り距離に補正日時を使う要件に対応するテストがない。
  - `22時台→補正後23時台`、`23時台→補正後翌日0時台` のような、補正と子時の合成境界がない。
  - `ST-02` は「非23時台」の条件がなく、23時台の意図的なV1.0差分と衝突する。
- 推奨:
  - 大運の節入り直前/直後、補正による年跨ぎ表示、22→23時、23→0時の統合テストを追加する。
  - `ST-02` を「補正なし・非23時台」に限定する。

### P1-06 禄命法の設計としては通変星記述が混在している

- 根拠:

## 5. 確認済みの整合事項

- 補正式: 入力時刻 + 手入力時差 + 地方平均時補正
- 時差符号: 出生地時計をJSTへ合わせる加算分を正
- 子時モード: `switch23` / `switch00`
- 既定値: `switch23`
- 時差範囲: `-23:59`〜`+23:59`
- 時刻未入力時: 補正なし、時柱なし
- 真太陽時、市区町村経度、DST自動適用は対象外
- PNGへ補正情報と子時モードを含める方針
